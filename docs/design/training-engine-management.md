# 训练引擎管理（Training Engine Management）

## 问题

部分训练引擎（如 Anima Fast）依赖独立运行时，体积可达数 GB，且需要显式安装 / 审计。  
若仅在「未就绪」时展示安装页、就绪后完全消失，用户无法判断当前是「已装好」还是「未安装」。  
后续还会有更多可选引擎（Musubi 等），不能为每个引擎复制一套安装页。

## 两层职责

| 层级 | 位置 | 职责 |
|------|------|------|
| 管理面 | 设置 →「训练引擎」 | 安装 / 重新安装 / 卸载、版本与路径摘要、日志、启用说明 |
| 使用面 | 训练页选中该引擎时 | 就绪：小号绿灯 +「训练环境准备就绪」；未就绪：完整状态条引导安装。管理入口只在设置页。 |

内置引擎（Kohya）始终 ready，管理页展示即可，训练页可不强制状态条。

## 默认引擎策略（重要）

**不要把 Anima Fast 设为产品全局默认。**

理由：

- Fast 运行时体积大、首次安装耗时长，且依赖 NVIDIA GPU。
- 新用户 / 整合包首次打开不应被默认选项拖进数 GB 下载。
- Kohya 与主 Python 环境绑定，开箱即用，适合作为冷启动默认。

推荐策略：

1. **冷启动默认**：`model=anima, engine=kohya, target=lora`（保持现状）。
2. **记住上次选择**（可选，默认开启）：同一模型下记住用户上次选的引擎；常用 Fast 的人回来仍是 Fast，但新人不会被动安装。
3. **设置页说明**：明确写出 Fast「非默认 / 体积大 / 需手动安装」，避免误解。

不采用：把 Fast 设成 Anima 模型的默认引擎。

## 统一状态机

所有可选引擎共用：

`not_installed | unknown | installing | auditing | ready | broken | disabled | coming_soon`

前端引擎目录声明：`id`、`kind`（`builtin` | `optional` | `planned`）、体积提示、能力标签。  
当前前端按统一路由 `/api/engines/<engine-id>/*` 读取各引擎状态（#302 已落地，替代原 `/api/plugins/*`）；后续可再收敛为 `GET /api/engines` 聚合接口。

## 操作命名（重要）

后端 `/repair` 实际是 **强制完整重装**，不是「找出坏了的部件再修」。

| 用户可见文案 | 含义 |
|---|---|
| 安装 | 首次安装 |
| 重新安装 | 完整重装（可能重新下载数 GB）；**不要叫「修复」** |
| 卸载 | 移除独立运行时 |
| 管理 | 进入设置页的引擎管理 |

规则：

- 训练页就绪后：小号绿灯 +「训练环境准备就绪」；不放「管理 / 重装 / 卸载」。
- 「重新安装」仅在环境异常（`broken` / `installed_unverified`）时可点；就绪时禁用，避免误点。
- 确认框必须写清：完整重装、可能重新下载数 GB。

真正的「修复」（只补缺依赖 / 修具体失败项）当前后端未提供；有了再单独做，勿用重装冒充。

## UI 要点

### 设置 · 训练引擎

- 引擎卡片列表：名称、状态、一句说明、体积/GPU 提示、操作按钮。
- Anima Fast：安装 / 重新安装（异常时） / 卸载 / 刷新；安装中展示进度与日志。
- Kohya：标记「内置 · 已就绪」。
- Musubi：标记「即将支持」。

### 训练页状态条

- 仅对 `optional` 且当前选中的引擎展示。
- 状态文案必须区分：已就绪 / 未安装 / 进行中 / 异常。
- 就绪后：训练页只显示小号绿灯 +「训练环境准备就绪」，不占整条卡片，也不放「管理」；管理入口只在设置页。
- 未就绪 / 异常：仍用完整状态条引导安装。

## 非目标（本轮）

- 不实现后端统一 `/api/engines`（可后续迁移）。
- 不在「开始训练」时静默全自动安装（可作为后续增强，且必须有进度 UI）。
- 不把 Fast 打进默认整合包强制预装。
- 不做「按失败项增量修复」（后端能力具备后再做）。
