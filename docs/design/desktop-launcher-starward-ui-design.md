研究对象是 [Scighost/Starward](https://github.com/Scighost/Starward)，本次冻结源码提交 `df8ae07b5ad4c9c6cb70d288488ce8073ce01478`。用户三张截图均为 1184×667，分别作为首页、设置导航和表单材质的主要视觉参考。来源、摘要和使用范围记录在素材说明中。

| 参考特征 | 采用方式 | 本项目适配 |
| --- | --- | --- |
| 56px 窄侧栏与小图标 | 按同一宽度、密度、选中条和上下分组还原 | 首页、版本、环境、日志；设置固定底部 |
| 大幅插画占据首页主体 | 清晰背景铺满内容区，左下和右下保留主要浮层 | 使用 Next Trainer 标识、版本摘要和服务主操作 |
| 蓝灰胶囊按钮 | 保留参考的低饱和色、圆角、按钮高度与留白 | 启动 / 打开训练器；运行时提供独立停止操作 |
| 设置页大面积模糊同源背景 | 复用首页背景色调，重模糊、压暗后承载表单 | 网络、外观、用户资料、安全与更新、关于 |
| 无框系统标题栏 | 标题栏与背景融合，右上保留标准窗口控制 | 关闭动作继续遵守现有任务确认与进程归属规则 |

## 3. 视觉规格

### 3.1 布局与尺寸

基准画布为 **1184×667**。建议新默认窗口采用该尺寸；现有产品为 900×600、最小 760×520，调整窗口下限是本稿待审核的建议：新最小布局按 **1024×640** 设计。实际实现还需验证 125% / 150% 缩放与键盘焦点。

| 元素 | 基准规格 |
| --- | --- |
| 主侧栏 | 56px；背景深色半透明；顶部与底部固定 |
| 顶部应用标识 | 40×40px，位于 x68 / y8 附近；采用本项目字母标识 |
| 导航命中区域 | 48×44px，图标约 20px，图标线宽约 1.4px |
| 选中状态 | 侧栏左侧约 3px 蓝灰竖条，按钮底色轻度提亮 |
| 标题栏 | 高约 48px；右侧系统按钮各 46×46px；关闭 hover 为红色 |
| 普通内容边距 | 侧栏后左留白 24px；主要区块间距 24–32px |
| 首页左下浮层 | 约 380px 宽；半透明深色底；版本、状态摘要、最近更新 |
| 首页主操作 | 固定右下，约 180×46px；次操作与主操作之间 12px |
| 设置二级导航 | 内容区左列约 256px；右侧正文从 x340 附近开始 |
| 表单与日志 | 只在内容区滚动；标题、筛选和主要操作保持可见 |

标题使用 22–24px 半粗体；主要版本文字 26–28px；正文 14px，辅助文字 12px。字体优先 `Segoe UI Variable` / `Microsoft YaHei UI` / 系统无衬线，日志使用系统等宽字体。

### 3.2 颜色与材质

| 角色 | 起始设计值 | 用法 |
| --- | --- | --- |
| 侧栏底色 | `#121b23`，透明度约 88% | 顶部至底部贯通 |
| 面板底色 | `#24343e`，透明度约 72% | 首页浮层、可交互表面 |
| 主强调色 | `#8c9db7` | 主按钮、选中控件、焦点 |
| 主文字 | `#f2f4f7` | 标题和主要内容 |
| 次文字 | `#bdcbd7` | 路径、说明、次操作 |
| 成功 / 警告 / 错误 | 柔和绿 / 琥珀 / 浅红 | 配合图标与文字，不仅靠颜色表达 |

首页保持背景清晰；其他管理页使用同源背景的约 40–72px 模糊与深色遮罩。文字区局部增加遮罩，保证正文可读。面板边框极细、阴影克制，避免整页堆叠不透明卡片。动画控制在 120–180ms；尊重系统减少动态效果设置。

### 3.3 背景与素材策略

本次审稿图从用户提供的截图提取局部插画与模糊材质，以便直接比较视觉。它们是**审稿参考素材**，不随之成为正式包的授权素材。正式背景使用自有或取得许可的插画，并支持用户选择本地图片、背景裁切、模糊和遮罩强度；图片解码失败时回退到蓝灰渐变。

不把 Starward 猫图标、游戏 Logo、角色头像直接改成 Next Trainer 品牌。原型使用本项目字母标识和自绘线性 SVG 图标。正式资源不得依赖运行时抓取游戏新闻或远程壁纸。

## 4. 页面和业务映射

### 4.1 侧栏

从上至下为：应用标识、首页、版本管理、环境管理、**日志**；底部固定设置。图标提供悬停提示、`aria-label`、当前页状态和键盘焦点。切页不触发安装全量检查，不清空日志，不暂停正在执行的任务。

### 4.2 首页

- 左上为 Next Trainer 标识与简短标题，中央保留背景视觉主体。
- 左下浮层提供“当前版本 / 最近更新”两项内容，显示真实版本、发布线、已安装状态和前往版本页的入口。无真实更新数据时显示“暂无更新信息”，不虚构新闻。
- 右下聚合服务状态与主操作。停止时显示“启动训练器”；启动时显示阶段文字及查看日志入口；健康后主按钮立即变为“打开训练器”，旁边提供停止与地址复制。
- 工作区路径和基础组件状态收纳为可展开详情，保留选择与检查入口；运行或变更期间遵守现有目录切换限制。
- 操作失败显示一条明确错误摘要及“查看日志”，点击后定位到本次操作。首页不再显示常驻长日志框。

首次未安装时沿用同一构图：左下解释即将安装的版本、空间和主要组件，主按钮改为“安装训练器”。可取消下载、阶段和真实进度继续显示；没有确定总量时使用不定进度。

### 4.3 版本管理

采用模糊背景、顶部页面标题、横向发布线切换和版本列表。当前版本有低饱和强调条；已安装、待安装、已知可用等状态分开显示。列表保留提交身份和必要的详细信息入口，普通用户不必面对大段摘要值。

下载 / 安装、选为当前、回退、移除继续按现有权限与计划执行；运行时禁止冲突变更。无合格稳定线时展示真实空状态。详细信任记录和高级操作进入“设置 → 安全与更新”，不删除底层验签、资料保护或修复能力。

### 4.4 环境管理

提供“主程序 / 训练引擎”分组，训练引擎包含 Kohya、Anima Fast、AI Toolkit、DiffSynth。按行展示名称、安装状态、上次检查时间和主要操作；展开后展示诊断、精准修复计划、独立解释器探测、重建与恢复等高级操作。

“已安装”“文件校验通过”“CUDA 可用”“本轮真实训练通过”分别表达，不能互相替代。原型演示数据只表示界面状态，当前实机依据仅支持 Kohya 的真实训练结论。

安装与修复阶段留在所选组件附近，长日志统一送入日志页。运行快照不会触发四引擎独立扫描。

### 4.5 独立日志页

日志成为一级导航页，正文占据主要区域。

| 区域 | 行为 |
| --- | --- |
| 顶部来源 | 全部、启动器、训练器服务、安装与修复；按工作区和当前会话明确分组 |
| 工具条 | 搜索、级别筛选、暂停/恢复跟随、复制所选/可见内容、导出 |
| 日志正文 | 时间、级别、来源、正文；错误不只依赖颜色；长行可横向滚动或切换换行 |
| 右下状态 | 新日志条数、是否暂停跟随；暂停时继续接收，点击提示回到底部 |
| 操作上下文 | 来自错误链接时定位对应 run / operation / seq，并突出该行 |
| 历史 | 查看当前与历史操作，不把清空显示误当成删除磁盘日志 |

页面间共享同一日志存储和订阅，切页保留筛选、选中和滚动位置。页面内使用有界缓冲和虚拟列表；磁盘读取分段，来源事件去重。复制与导出前对凭据、代理账号等敏感字段脱敏。原来只有文本的日志事件可以兼容显示为“未分类”，不伪造历史时间戳或级别。

当前桌面壳负责启动器与服务日志；训练任务的完整历史和指标仍由训练器网页提供。日志页可以链接到当前任务日志，首版不额外建设训练任务数据库或跨进程历史聚合平台。

### 4.6 设置

二级导航采用截图中的纵向列表，右侧表单保留留白；有修改时底部出现“应用”操作条。

| 设置项 | 现有能力与本次视觉适配 |
| --- | --- |
| 外观 | 本次新增：本地背景、背景遮罩/模糊、减少动态效果、日志字号；暗色为本稿基准 |
| 网络 | 搬迁现有系统/手动/直连设置、代理与本机绕过、诊断；不恢复下载额度 |
| 用户资料 | 搬迁工作区路径、资料目录、导入预览和冲突处理入口 |
| 安全与更新 | 搬迁可信清单、版本身份、独立壳更新/恢复；生产渠道未配置时据实显示 |
| 关于 | 启动器版本、训练器版本、开源许可、项目与问题反馈链接 |

设置改动的写入仍使用原有计划、确认和原子提交合同。没有实际接入的项目在设计原型中仅演示，不会在现行程序中生效。

## 5. 启停状态优化设计

### 5.1 已核实的原因

当前启动命令 `Engine::start()` 在服务健康并输出就绪日志后调用 `self.inspect(root)`；`inspect()` 会检查 Python、源码、环境，并在版本列表遍历中对当前版本再检查一次。前端只在完整命令结束后替换 `Report`。停止则先完成 `stopTrainer()`，随后再等待全量 `inspect`，旧的 running 状态仍决定按钮。

代码位置和调用链见 [runtime-research.md](desktop-launcher-ui-review/runtime-research.md)。本轮没有启停实测，不给这些函数套用未经测量的固定耗时；健康记录提交本身也需单独计时。

### 5.2 状态契约

拆成两类状态：

1. **安装评估**：完整性、配方、版本、环境、资料绑定、检查时间与修复结果；在安装、修复、切换、显式检查和启动前必要校验时产生。
2. **服务状态**：本次自有进程、健康、端口、启动/停止阶段与错误；由独立短锁快照和结构化事件产生，不读整个 venv、不执行 imports。

拟新增 `RuntimeSnapshot`、`runtime_status(root)` 和 `launcher:runtime` 事件。快照携带工作区、版本、实例、binding generation、run_id、seq、phase、url、退出信息和时间。`run_id + seq` 防止旧回调覆盖新状态。轻量读取不能再次排队等待当前 Engine 大锁。

| 阶段 | 显示 | 主操作和保护 |
| --- | --- | --- |
| stopped | 可以启动 | 启动训练器，后端仍做必要启动前校验 |
| checking | 正在检查启动条件 | 导航/日志可用，重复启动和冲突变更禁用 |
| starting | 正在启动，等待服务 | 允许取消本次启动并回收本次 Job |
| ready | 服务已就绪 | 打开训练器、停止服务、复制地址 |
| degraded | 进程运行，服务暂不可达 | 保留停止；可重新检查连接，不重复启动 |
| stopping | 正在停止 | 防重复，日志可用 |
| stopped / exited | 已停止 / 服务已退出 | 确认 Job 排空和租约回收后恢复启动 |
| start_failed / stop_failed | 失败摘要与查看日志 | 保留真实运行上下文；失败不伪报停止或就绪 |

启动前的可信源码、解释器、环境、绑定、租约与端口归属检查保留。健康提交完成后直接发布 ready，不再通过尾部完整检查决定按钮。停止后直接返回本次生命周期结果。完整检查仍有自己的入口、进度与时间，后台检查不会覆盖健康服务的运行事实。

生命周期由单一 owner 串行操作 Child / Job / lease，短锁只用于读取已维护的快照。健康绑定提交后再次确认 run / generation 仍为当前、停止尚未开始，才发布 ready；自有 Job 完全排空且 lease 释放后才发布 stopped。不能因拆锁允许两个动作同时操作同一进程对象。

异常退出主动发布事件；前端先订阅再读取快照，事件丢失时用轻量快照兜底。打开网页时继续即时验证自有监听者与健康。不能根据日志包含“启动成功”几个字决定状态。

### 5.3 响应验收目标

以下是待实现后验证的目标：

| 测量 | 目标 / 允许上限 |
| --- | --- |
| 点击启动或停止到显示过渡状态 | 100ms / 250ms |
| 必要健康提交完成、服务归属与健康成立到网页按钮可用 | 250ms / 1s |
| 自有 Job 排空和租约回收到启动按钮可用 | 250ms / 1s |
| 受管服务意外退出到 UI 撤销 ready | 事件目标 1s；丢事件兜底 2s |
| 切换页面和打开日志 | 100ms / 250ms，不触发全量检查 |

这些指标约束**已经完成后的状态反馈**，不承诺 Python 冷启动、首次安装或完整文件校验在一秒内结束。将点击、校验开始/结束、进程生成、健康响应、健康提交、事件发布、UI渲染、Job排空分别计时，避免将不同等待混在一起。
