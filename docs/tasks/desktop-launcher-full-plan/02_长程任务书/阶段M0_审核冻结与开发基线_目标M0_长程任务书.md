把底座安全保存为开发基线，冻结审核结论与可兑现的资源条件，使后续开发可以复现、恢复和验收。用户已启动执行并批准CR-001/002；WIP和原资源失败已保存，实际证据见总控与探针报告。以下Phase按0.3明确范围执行，M0退出仍需真实复审及完整保存。

- 包含规格/审核冻结、Git归属、基线检查、四引擎资源和干净 Windows 的提前可行性核查。

- 用户开始指令已使D1–D6推荐项及原预算生效；公共发布/生产身份仍不自动授权。

## 执行阶段

### Phase 1：冻结本次审核与规格身份

- Purpose（目的）：先消除产品范围与授权歧义，再进行变更。
- 步骤：逐项记录D1–D6用户原文选择、日期、接受版本、限制及相对推荐方案的差异。
- 步骤：重新读取issue #516与本地快照比对；新增需求按变更控制处理，网络不可达保持明确记录。
- Outputs（输出）：审核记录、规格/计划SHA256、需求到M0–M6映射和授权资源边界。
- Completion criteria（完成条件）：没有未决的实现范围；未授权内容不能悄悄放入后续步骤。
- Validation（验证）：独立核对审核原文、设计摘要与总控；内部复审只作为设计证据。
- Evidence（证据）：`M0/audit-freeze.md`、规格摘要和需求快照对照。
- Failure handling（失败恢复）：缺用户审核则停止开工，保留drafting并报告最小缺口。

### Phase 2：保护工作树并建立精确归属

- Purpose（目的）：保存底座成果且不混入其他功能。
- 步骤：记录HEAD、分支、origin、工作树/暂存区、untracked清单和原始文件SHA；对照规划前快照。
- 步骤：按Git治理生成逐文件allowlist及来源，包含必要底座/本计划文件；新增归属须有解释。
- 步骤：固定候选策略：每批worker/引擎改动精确提交并普通push后，以完整feature提交生成可重取归档/前端/配方及SHA；测试catalog显式候选，不默认标main稳定，receipt保留实际源码身份。
- Outputs（输出）：精确allowlist、变更前后摘要和不会纳入本阶段的路径清单。
- Completion criteria（完成条件）：每个候选路径有归属；其他功能文件可证明仍在原位且内容保持。
- Validation（验证）：逐项读取差异与暂存差异；禁止`git add -A`、reset、clean或从HEAD覆盖成果。
- Evidence（证据）：`M0/git-before.json`、`M0/source-allowlist.txt`、逐文件SHA和差异记录。
- Failure handling（失败恢复）：归属不清只暂停该候选；不以删除、回滚工作树或整目录暂存解决。

### Phase 3：验证可复现的开发基线

- Purpose（目的）：确认已保存的底座能成为后续实现起点。
- 步骤：记录Rust/Node/npm/Python工具路径及版本；核对锁文件与已有依赖，避免无关升级。
- 步骤：运行下文已存在的构建/检查入口和与底座变更相关的Python测试，保留原始失败。
- 步骤：从allowlist快照准备隔离新根，写最小证据探针核验现有junction/`.python`布局、只读副作用和取消锁基线；研发overlay仅作探针，不抵扣后续已归档候选的安装/训练或最终验收。
- Outputs（输出）：命令/环境/退出码、测试结果与既有缺陷归属；本轮规划不预填成功数。
- Completion criteria（完成条件）：必要检查通过或有经审计的范围调整；本阶段开工前提P0/P1不能带入下一阶段，后续风险按分期技术门继续阻断。
- Validation（验证）：由另一审查者核对源文件、日志与实际命令，不引用旧测试次数冒充重跑。
- Evidence（证据）：`M0/baseline-checks/`、依赖与工具版本表。
- Failure handling（失败恢复）：保留日志，区分环境/既有底座/无关功能问题；不扩大修改范围。

### Phase 4：提前证明验收资源可得

- Purpose（目的）：在开发前发现机器、模型和预算硬阻塞。
- 步骤：保留干净Windows镜像/VM、许可、缺WebView2核查及原失败，P1原结果blocked；按CR-002登记调度状态`deferred by CR-002`，由M5相应系统动作及Phase6专项验证开始前补齐合法可用资源、真实基线和恢复条件，不将延期记pass/skip。
- 步骤：四引擎逐项列合法模型/数据来源、许可、摘要、大小、最低显存/配置与预算可行路径；来源不可靠则具体阻塞。
- 步骤：按CR-001保留独立P3原超时/partial，不再单独重试；对应CUDA小张量证据进入M2/M3真实引擎配方。M0不先下载四模型；完整架构加载/最小反向探针仍按未豁免范围在M2/M3前置验证，未测项保持pending。
- Outputs（输出）：资源矩阵、累计网络/磁盘/GPU台账、单次时限与清理边界；缺口标unknown/blocked。
- Completion criteria（完成条件）：合法资产/最低配置与预算有可信可行路径；P1按CR-002明确M5承接及硬截止，P3按CR-001分期，原blocked/not-run均留证、不作pass。其余M0资源/安全门真实通过；总网络200GiB、F峰值300GiB、GPU180分钟和原阶段限额不变，不能擅自突破或调剂。
- 资源限额提案：M0新增网络≤10GiB、GPU≤10分钟，计入全计划累计；F剩余≥100GiB、E剩余≥20GiB等总门同步适用。
- Validation（验证）：核对实际空闲空间、驱动、合法资产与资源账本；P1原许可/启动缺口及M5承接不得省略，不能仅看文件名或设备识别冒充资源就绪。
- Evidence（证据）：`M0/resource-feasibility/`，每引擎模型许可/配置/预算和干净系统探针结果。
- Failure handling（失败恢复）：先停重型操作，保留未完成门；不得删除旧现场、默默换大机器或降低四引擎标准。

### Phase 5：独立复审并保存阶段基线

- Purpose（目的）：让下一阶段依赖已审查且确实保存到远端的基线。

- Validation（验证）：按Git治理核验提交父关系/文件范围和远端当前值；总控是唯一进度记录位置。
- Evidence（证据）：`M0/stage-completion.md`、`M0/independent-review.md`、推送回执。
- Failure handling（失败恢复）：网络/远端并发失败按治理恢复；禁止force push，未核验远端则M0保持未完成。
