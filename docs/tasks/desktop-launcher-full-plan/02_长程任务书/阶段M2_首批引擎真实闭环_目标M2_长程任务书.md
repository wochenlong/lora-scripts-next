## 执行阶段

### Phase 1：先验证RuntimeLayout路径合同

- Purpose（目的）：先解决现有run联接和基础Python归属的静态冲突。
- 步骤：定义source/run/profile/engine_state/base_python/environment_instance根及允许物理根、所有者和迁移规则。
- 步骤：真junction探针覆盖run/extensions外指profile后Anima `_resolve_child`拒绝情形，以及重建run后的`.python`稳定性。
- Outputs（输出）：布局合同、固定发布状态/环境实例路径、兼容映射和显式迁移计划。
- Completion criteria（完成条件）：允许映射通过、任意外指拒绝；重建run不丢Python/环境，不能删除路径保护绕过。
- Validation（验证）：中文空格路径、junction替换、非法reparse目标、重复恢复与旧CLI路径对照。
- Evidence（证据）：`M2/runtime-layout/`，物理/逻辑路径、前后摘要和拒绝结果。
- Failure handling（失败恢复）：保留旧映射/registry副本，布局门不通过不得开始引擎安装。

### Phase 2：建立独立worker与双入口共享控制核心

- Purpose（目的）：主GUI损坏时仍能诊断并修复引擎。
- 步骤：worker由校验过的基础Python启动，最小依赖；禁止启动链导入GUI、Torch或整套`mikazuki.app`。
- 步骤：抽取纯配方/事实/计划/执行核心；网页与桌面复用动作、operation和跨进程锁，CLI通过兼容层调用。
- 步骤：分离`inspect_readonly`、`probe_execute`、`repair_apply`；旧status/preflight可能写配置，不能直接包装成只读。
- Outputs（输出）：类型化控制协议、能力声明、隔离入口和只读前后摘要合同。
- Completion criteria（完成条件）：GUI缺包仍可启动worker；基础Python坏先由Rust恢复；探针临时文件只写受管目录。
- Validation（验证）：屏蔽GUI/Torch import，损坏GUI后执行只读/修复；网页/桌面并发动作只能一个获得写lease。
- Evidence（证据）：`M2/worker/`，import边界、双入口事件、锁和文件前后SHA。
- Failure handling（失败恢复）：无法只读的旧入口标不支持并改造；不偷跑repair或回退到GUI环境。

### Phase 3：冻结两引擎独立配方与所有权

- Purpose（目的）：让每个环境有明确Python/ABI、上游/补丁和依赖目标。
- 步骤：核对Kohya当前Python3.10、Anima Fast当前3.13要求，冻结精确patch、平台wheel和全部相关资产摘要。
- 步骤：Kohya受管模式仅standalone，禁止main_env fallback/upgrade写GUI；非受管旧行为通过明确边界保留。
- 步骤：把含本阶段worker/引擎改动的候选T按精确范围提交、普通push并核实完整SHA，再生成/锁定训练器归档、前端资产和配方；测试catalog/receipt显式绑定T，不默认冒充main稳定。候选WIP推送不解锁阶段退出门，最终C/S仍按治理保存。
- Outputs（输出）：两份配方、依赖锁/补丁摘要、探测命令ID、GPU要求和可用修复动作。
- Completion criteria（完成条件）：与GUI3.10.19的基础/环境所有权分清；可变或不可重现资产明确限制且不宣称冻结完成。
- Validation（验证）：配方摘要绑定operation/receipt；用小夹具核对解释器prefix/base_prefix、依赖和补丁字段及绑定合同，不导入真实引擎实测。
- Evidence（证据）：`M2/recipes/`，来源/许可/完整SHA及Kohya受管/非受管兼容矩阵。
- Failure handling（失败恢复）：缺锁、资产或许可停在此门；不得修改GUI依赖补齐引擎。

### Phase 4：独立检查与分层状态冒烟

- Purpose（目的）：实现并区分检查、诊断与实际变更，以小夹具核对状态表达。
- 步骤：实现两引擎固定实例路径与安装控制，复用M1的下载/取消/dirty/快照/绑定事务；不安装真实引擎做验收。
- 步骤：以合成结果核对安装/导入/GPU/训练各层状态，以及未知、权限、超时和跳过的表达；硬件页区分驱动CUDA与Torch编译CUDA。
- 步骤：调用各引擎检查/诊断入口，核对目标路径、配方和解释器绑定；真实安装/导入、GPU小张量、模型加载/最小反向均 `skip + CR-004`。
- Outputs（输出）：两引擎小夹具状态结果、解释器/路径绑定、配方与依赖/上游指纹。
- Completion criteria（完成条件）：没有nvcc不自动判不支持；未知/权限/超时不显示未安装；GUI健康不代表引擎健康。
- Validation（验证）：核对候选T/recipe/catalog/receipt与worker/前端归档身份，用少量小夹具验证检查入口、未知状态拒写和非目标摘要；原始main/dev加开发repo overlay不得作为交付身份。
- Evidence（证据）：沿用 `M2/kohya/install/`、`M2/anima-fast/install/` 保存冒烟结果与CR-004跳过说明，不新增报告体系。
- Failure handling（失败恢复）：按固定实例和引用闭包恢复，不能证明则dirty禁启；不把安装完成记训练已通过。

### Phase 5：每引擎RepairPlan与精准修复冒烟

- Purpose（目的）：实现独立修复并以小夹具证明计划、变更和失败保护只影响目标。
- 步骤：分别准备合成/小夹具登记、包/源码和解释器状态，入口返回可解释的最小RepairPlan。
- 资源边界：仅使用必要小夹具/工具并记资源总账；旧网络≤60GiB/GPU≤40分钟与训练步数预算属历史上限，本阶段不据此下载模型或启动GPU/训练。
- 步骤：每引擎选必要修复成功分支，覆盖dirty/generation、lease、路径隔离与未知状态失败拒写，按影响选择少量中断/恢复分支。
- 步骤：核对包已改未提交窗口保持dirty、固定实例路径恢复、非目标摘要不变；真实引擎破坏/修复/再训练及权重读取核验统一 `skip + CR-004`。
- Outputs（输出）：两引擎既有矩阵中的检查/计划/修复冒烟结果；GUI控制通道与另一引擎独立证据。
- Completion criteria（完成条件）：两引擎必要入口、状态、计划和成功/拒绝/恢复分支通过，非目标hash不变；跳过项不作pass。
- Validation（验证）：入口到worker的动作/锁/事件与小夹具前后摘要一致；只验证必要分支，复用未受影响证据。
- Evidence（证据）：沿用 `M2/kohya/train-repair/`、`M2/anima-fast/train-repair/`，注明本次为冒烟、真实训练 `skip + CR-004`。
- Failure handling（失败恢复）：保留最小失败现场与dirty状态；控制合同失败仍阻塞对应门，GPU/模型资源不作为本阶段完成前置。
