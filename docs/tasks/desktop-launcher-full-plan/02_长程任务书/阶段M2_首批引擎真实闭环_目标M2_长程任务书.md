用共享、独立于GUI的控制核心完成Kohya和Anima Fast的真实安装、分层诊断、精准修复与GPU短训练，并证明两引擎/GUI相互隔离。本文为待审计划，本轮不执行安装或训练。

## 范围与约束

- M1完成门和M0资源可行性先通过；D1–D6采用推荐方案仅为本次规划假设。
- 两引擎按发布隔离，下载缓存可共享、环境实例不能盲目共享；不能把普通Anima训练冒作Anima Fast。
- 旧CLI兼容保留，不支持新合同的历史发布仅保留已验证GUI能力并标明引擎待适配。
- 遵守[Git治理](../00_预检证据/git-baseline-governance.md)、[测试治理](../00_预检证据/testing-and-evidence-governance.md)、[资源授权](../00_预检证据/risk-and-authorization-governance.md)。
- 只在新沙盒内使用合法模型/数据和批准配额，实际显存/时长不够则阻塞，不能以导入替代训练。

## 执行阶段

### Phase 1：先验证RuntimeLayout路径合同

- Purpose（目的）：先解决现有run联接和基础Python归属的静态冲突。
- 步骤：定义source/run/profile/engine_state/base_python/environment_instance根及允许物理根、所有者和迁移规则。
- 步骤：真junction探针覆盖run/extensions外指profile后Anima `_resolve_child`拒绝情形，以及重建run后的`.python`稳定性。
- Outputs（输出）：布局合同、固定发布状态/环境实例路径、兼容映射和显式迁移计划。
- Completion criteria（完成条件）：允许映射通过、任意外指拒绝；重建run不丢Python/环境，不能删除路径保护绕过。
- Validation（验证）：中文空格路径、junction替换、非法reparse目标、重复恢复与旧CLI路径对照。
- Evidence（证据）：`M2/runtime-layout/`，物理/逻辑路径、前后摘要和拒绝结果。
- Failure handling（失败恢复）：保留旧映射/registry副本，布局门不通过不得开始引擎安装。

### Phase 2：建立独立worker与双入口共享控制核心

- Purpose（目的）：主GUI损坏时仍能诊断并修复引擎。
- 步骤：worker由校验过的基础Python启动，最小依赖；禁止启动链导入GUI、Torch或整套`mikazuki.app`。
- 步骤：抽取纯配方/事实/计划/执行核心；网页与桌面复用动作、operation和跨进程锁，CLI通过兼容层调用。
- 步骤：分离`inspect_readonly`、`probe_execute`、`repair_apply`；旧status/preflight可能写配置，不能直接包装成只读。
- Outputs（输出）：类型化控制协议、能力声明、隔离入口和只读前后摘要合同。
- Completion criteria（完成条件）：GUI缺包仍可启动worker；基础Python坏先由Rust恢复；探针临时文件只写受管目录。
- Validation（验证）：屏蔽GUI/Torch import，损坏GUI后执行只读/修复；网页/桌面并发动作只能一个获得写lease。
- Evidence（证据）：`M2/worker/`，import边界、双入口事件、锁和文件前后SHA。
- Failure handling（失败恢复）：无法只读的旧入口标不支持并改造；不偷跑repair或回退到GUI环境。

### Phase 3：冻结两引擎独立配方与所有权

- Purpose（目的）：让每个环境有明确Python/ABI、上游/补丁和依赖目标。
- 步骤：核对Kohya当前Python3.10、Anima Fast当前3.13要求，冻结精确patch、平台wheel和全部相关资产摘要。
- 步骤：Kohya受管模式仅standalone，禁止main_env fallback/upgrade写GUI；非受管旧行为通过明确边界保留。
- 步骤：把含本阶段worker/引擎改动的候选T按精确范围提交、普通push并核实完整SHA，再生成/锁定训练器归档、前端资产和配方；测试catalog/receipt显式绑定T，不默认冒充main稳定。候选WIP推送不解锁阶段退出门，最终C/S仍按治理保存。
- Outputs（输出）：两份配方、依赖锁/补丁摘要、探测命令ID、GPU要求和可用修复动作。
- Completion criteria（完成条件）：与GUI3.10.19的基础/环境所有权分清；可变或不可重现资产明确限制且不宣称冻结完成。
- Validation（验证）：配方摘要绑定operation/receipt；实际解释器prefix/base_prefix、依赖和补丁与合同一致。
- Evidence（证据）：`M2/recipes/`，来源/许可/完整SHA及Kohya受管/非受管兼容矩阵。
- Failure handling（失败恢复）：缺锁、资产或许可停在此门；不得修改GUI依赖补齐引擎。

### Phase 4：真实安装与独立分层探测

- Purpose（目的）：从实际解释器和文件证明引擎安装状态。
- 步骤：分别在最终不变实例路径安装两引擎，复用M1的下载/取消/dirty/快照/绑定事务。
- 步骤：分别报告安装完整、可导入、GPU小张量、最小训练四层状态；硬件页区分驱动CUDA与Torch编译CUDA。
- 步骤：在本阶段预算内完成对应架构模型加载/最小反向资源探针，正式训练验收前关闭M0留下的完整架构显存未测项，不能以CUDA微探针替代。
- Outputs（输出）：两引擎安装报告、解释器/模块位置、GPU运算结果和依赖/上游指纹。
- Completion criteria（完成条件）：没有nvcc不自动判不支持；未知/权限/超时不显示未安装；GUI健康不代表引擎健康。
- Validation（验证）：实际安装的trainer源码、前端/归档SHA、worker入口与候选T/recipe/catalog/receipt逐项一致，再实测解释器、中断恢复和非目标摘要；原始main/dev加开发repo overlay不得作为闭环证据。
- Evidence（证据）：`M2/kohya/install/`、`M2/anima-fast/install/`及GPU小张量原始结果。
- Failure handling（失败恢复）：按固定实例和引用闭包恢复，不能证明则dirty禁启；不把安装完成记训练已通过。

### Phase 5：每引擎短训练与精准修复闭环

- Purpose（目的）：证明训练真实可用，且故障修复只影响目标。
- 步骤：按M0确认的合法小模型/数据和16GiB本机可行配置，分别冻结步数/分辨率/批次/时限和输出目录。
- 资源提案：M2新增网络≤60GiB、GPU总≤40分钟；单次最多20 optimizer steps或10分钟先到即止，失败重试计入全计划同引擎最多2次，统一GPU lease串行。
- 步骤：执行训练保存loss/实际步数/退出码、GPU峰值与权重SHA；对应格式读取器实际打开并核验非空张量、预期键、shape/dtype和有限值，不能只停留dry-run。
- 步骤：分别注入登记丢失、单包/源码故障和依赖已改未提交中断，预览闭包后修复并重新训练。
- Outputs（输出）：两套独立训练与故障修复报告；GUI坏仍修引擎、引擎坏不阻GUI以及另一引擎不变证据。
- Completion criteria（完成条件）：两引擎均四层通过；短训练实际产物可检查，非目标hash不变；超预算停止并报告。
- Validation（验证）：原生UI按钮到worker、训练进程/监听器归属、产物、repair前后探测与再训练结果相互印证。
- Evidence（证据）：`M2/kohya/train-repair/`、`M2/anima-fast/train-repair/`及参数/模型许可/资源累计。
- Failure handling（失败恢复）：保留最小失败现场与dirty状态；资源不足不得减为仅导入，按变更控制解决。

### Phase 6：首批受限预览评估与阶段保存

- Purpose（目的）：提供可核查的首批能力结论并解锁M3。
- Outputs（输出）：两引擎/A5/A6追踪、受限预览前提、未适配引擎说明、独立复审和阶段完成报告。
- Completion criteria（完成条件）：真实证据齐，无未关闭P0/P1；本阶段commit、普通push `origin feat/desktop-launcher`和`ls-remote`完整SHA回执齐。
- Validation（验证）：复审来源/锁/路径/训练证据；按Git治理核实代码C和状态S两次push及外部回执；评估已有WebView2预览，不宣称干净机正式分发。
- Evidence（证据）：`M2/stage-completion.md`、`M2/independent-review.md`、Git回执。
- Failure handling（失败恢复）：有必测not-run、训练失败或远端未保存则不进入M3；不以支持列表补证据。
