## 执行阶段

### Phase 1：先冻结GUI配方与环境实例合同

- Purpose（目的）：让安装、恢复和定点修复有可验证的目标身份。
- 步骤：冻结平台/Python精确版本与ABI、依赖闭包、工具、源码和补丁SHA，说明镜像相同制品约束。
- 步骤：设计旧固定GUI实例的显式registry升级、实例ID/generation和新旧schema写保护。
- 步骤：在M1内部先运行P6本地HTTP/慢子进程最小样机，核验独立取消及包已变更窗口的dirty/快照恢复，通过后才进入操作/修复主要实现；不要求M0先完成M1功能。
- Outputs（输出）：内置GUI配方、预算/摘要、实例/绑定合同和兼容测试向量。
- Completion criteria（完成条件）：同配方资产身份明确；未知/不兼容格式拒绝变更并保存旧副本。
- Validation（验证）：配方与实际安装文件/解释器一致；不以可变版本范围代替锁。
- Evidence（证据）：`M1/recipe/`、schema向量和来源清单。
- Failure handling（失败恢复）：锁不全的组件不宣称可复现；先补资产合同，不绕过哈希安装。

### Phase 2：实现可独立控制的操作管理

- Purpose（目的）：使长操作不阻塞取消、UI读取和恢复判断。
- 步骤：操作独立ID，phase/status分离，持久检查点/事件序号/重试次数/错误码，兼容读取旧journal。
- 步骤：取消采用独立原子标志或通道，不等待长Engine Mutex；跨进程workspace lease覆盖所有变更入口。
- Outputs（输出）：操作管理器、非阻塞IPC/事件与CLI最终报告兼容层。
- Completion criteria（完成条件）：长任务中取消可达；安全提交延迟取消可解释；双进程不能同时变更。
- Validation（验证）：竞争、事件断线补读、重复请求、关窗及杀进程后以磁盘事实恢复。
- Evidence（证据）：`M1/operations/`状态/事件/进程日志及取消时延。
- Failure handling（失败恢复）：未知状态保留并拒绝覆盖；只回收本次操作拥有的进程。

### Phase 3：实现网络一致性、严格续传和资源计量

- Purpose（目的）：防止错误续传、代理漂移、ZIP超限污染安装。
- 步骤：Rust、uv、Git和worker共享标准化网络策略；直连/手动/系统/环境及绕过语义用共享向量对照。
- 步骤：partial绑定资产/大小/来源/已写字节/ETag或Last-Modified；只有206且Content-Range起点/总长正确才追加。
- 步骤：200重新开始；416、验证器变化先核对；跨镜像条件全部满足才复用；结束全文件SHA256。
- Outputs（输出）：受控下载缓存、连接分类诊断、实际字节/解压条目/压缩比计量与安全拒绝。
- Completion criteria（完成条件）：无静默直连；下载、写出和重试均计入授权预算；ZIP链接/穿越/重名被拒。
- Validation（验证）：本地HTTP夹具覆盖截断、Range忽略/错误、源改变、416及ZIP/磁盘异常。
- Evidence（证据）：`M1/downloads/`、HTTP请求/响应摘要、完整SHA、网络/磁盘台账。
- Failure handling（失败恢复）：不可信partial隔离/重下；旧健康绑定不变，保留失败原始原因。

### Phase 4：实现受保护的最小修复事务

- Purpose（目的）：缺一个包时只改必要闭包，并能解释中断后环境状态。
- 步骤：只读诊断生成固定RepairPlan，列事实摘要、路径/依赖闭包、预算、锁、快照和验收器；执行前重核。
- 步骤：停止目标使用者→独立snapshot→持久化instance/generation/dirty→修改；快照不能用会被写穿的硬链接。
- 步骤：Windows venv在最终固定实例路径创建；通过绑定原子激活，不把staging venv rename作发布。
- 步骤：commit intent先记旧绑定/旧generation、候选摘要和回滚材料；基础Python按受管引用闭包停用并逐环境复验。
- Outputs（输出）：登记补齐、单包/源码/Python分项修复及明确后备重建，保留非目标组件。
- Completion criteria（完成条件）：取消不清dirty；失败同绝对路径恢复并重验，不能证明则禁止启动该实例。
- Validation（验证）：在包文件已改且状态未提交窗口强杀；恢复快照、绑定和真实解释器/入口交叉核查。
- Evidence（证据）：`M1/repair/`，RepairPlan/快照摘要/intent/前后hash/实际探测。
- Failure handling（失败恢复）：保持dirty并提供继续修复或已验证旧绑定回退；不把进程结束当恢复成功。

### Phase 5：原生UI与真实故障闭环

- Purpose（目的）：证明用户能通过实际界面完成安装、取消、恢复和修复。
- 步骤：三页显示组件事实、结构化进度、修复影响与错误；首次安装默认只选GUI，依批准D1行为选择发布线。
- 步骤：沙盒运行下载/解压/依赖/提交各点取消、关窗、断网、强杀、重启恢复、空间不足与代理错误矩阵。
- Outputs（输出）：真实GUI安装/启动/损坏/修复/回退报告、截图和资料/非目标组件保护对照。
- Completion criteria（完成条件）：用户操作与operation/receipt/绑定一致；无假100%，回退不重新下载已验证旧版。
- Validation（验证）：原生按钮/窗口、900×600滚动/长路径/键盘、API和资源文件语义、监听器及外部服务对照。
- Evidence（证据）：`M1/real-cycle/`及`M1/fault-matrix/`；本阶段不声称干净机/引擎训练通过。
- Failure handling（失败恢复）：保存失败现场，修正后复验受影响链；不删除资料或复用错误健康记录。

### Phase 6：复审与保存阶段成果

- Purpose（目的）：使M2建立在完整、已保存的恢复基础上。
- Outputs（输出）：阶段完成报告、A2/A3/A5/A7追踪、not-run表及独立复审。
- Completion criteria（完成条件）：必测通过，无未关闭P0/P1，commit/普通push `origin feat/desktop-launcher`/`ls-remote`完整SHA回执齐全。
- Validation（验证）：按Git治理精确暂存、检查提交范围，代码C和状态S分别push核实，外部baseline-final.json收录S；只更新总控阶段状态。
- Evidence（证据）：`M1/stage-completion.md`、`M1/independent-review.md`、Git回执。
- Failure handling（失败恢复）：缺任一完成门则不进入M2；网络失败不force push或伪记已保存。
