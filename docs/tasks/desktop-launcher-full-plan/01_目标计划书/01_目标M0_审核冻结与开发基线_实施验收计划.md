## 目标与回答的问题

在用户审计后形成可重现、可提交、资源可行的开发起点，回答“后续实现是否已有批准的规格、明确的代码边界和可兑现的验收资源”。本轮只编写计划；D1–D6 推荐项仍是规划假设。

## 范围与前置条件

- 包含 D1–D6 审核冻结、代码/文档归属清单、现有底座基线验证、Git 关系和资源预检。
- 不含新安装器实现、旧安装改写或全量引擎验收；只在批准资源范围内执行最小可行性探针，旧底座计划保持已完成历史。
- 开工需用户完成本次审计，明确执行范围；资源授权按[风险与授权治理](../00_预检证据/risk-and-authorization-governance.md)另行核对。
- 分支为 `feat/desktop-launcher`；基线提交和隔离范围按[Git 基线治理](../00_预检证据/git-baseline-governance.md)执行。

## 验收标准

1. D1–D6 每项有用户选择、影响与冻结时间；未审项保持待审，不将内部设计复审当用户批准。
2. 记录 HEAD、origin URL、远端分支关系、全部 dirty/untracked 路径和逐文件 SHA256；底座归属采用精确 allowlist。
3. 基线仅提交审核范围，禁止 `git add -A`；其他功能及其文档完整保留，暂存区逐项复核。
4. 现有 Rust/前端和相关 Python 基线检查有原始输出；失败先说明既有/新增来源，不能以旧成功报告替代本轮结果。
5. 保留已完成的干净Windows资源核查与原失败；P1合法可用、可启动且缺WebView2的资源实际就绪按CR-002延期到M5相应系统动作及Phase6分发专项验证开始前，原结果blocked，调度状态`deferred by CR-002`，不计pass/skip。四引擎合法资产、最低显存/配置和预算仍须形成可行路径，本机约16GiB不设为产品硬限制；完整模型加载/反向探针留在M2/M3前置门。
6. 下载、缓存/解压/快照磁盘峰值、GPU时长及清理边界有明确预算；除CR-001指定GPU子项和CR-002指定P1时点外，资源或许可不足仍阻断相应任务。P1不得再延期到M6，也不因时点调整增加或调剂预算。
7. 冻结候选源码策略：后续worker/引擎改动必须包含于实际安装的已推送完整feature提交，归档/前端/配方逐项锁SHA；测试catalog明确候选身份，不默认冒充main稳定版。开发工作树overlay只作研发探针，不能抵扣阶段/最终安装验收。

退出需CR-002授权与M5承接明确、其余M0真实证据和阶段完成报告齐备、独立复审无本阶段未关闭P0/P1，以及按Git治理完成代码C/状态S两次普通push `origin feat/desktop-launcher`并核实远端完整SHA；后续技术风险仍受分期门约束。批准CR-002或保存WIP不等于M0完成；真实退出后仅解锁M1开工核对。
