# 变更控制与防漂移

规格源为[后续设计书](../../../design/desktop-launcher-next-design.md)，执行状态源为[总控索引](../00_总控目标索引.md)。当前计划0.2；用户已启动执行，并于2026-10-29批准下列CR-001。历史底座和0.1失败证据保留。

## CR-001：用户批准跳过受资源限制的GPU验收

- 日期/状态：2026-10-29（Asia/Shanghai），**approved（用户明确批准）**；计划/规格从0.1修订为0.2，阶段名和顺序保持M0–M6。
- 授权原文：用户对“Fast要求驱动≥595、本机591.86，DiffSynth完整BF16 TE超过显存；是否有合适CUDA测试机”的异步问题回复：**“没有合适机器，跳过这个测试”**。原文与0.1逐文件备份保存在当前run的`changes/CR-001/authorization.json`及`before/`。不重复申请此豁免。
- 原要求：P2/P3确认四引擎GPU资源可得，M2/M3和M6分别完成四引擎真实GPU运算、模型加载/反向、短训练及权重回读；任一缺资源阻断阶段。
- 本次变化：Anima Fast固定驱动不满足的真实GPU运算/模型加载/反向/短训练/输出权重，以及DiffSynth完整BF16模型资源受限的加载/反向/短训练/输出权重，分别记录 **`skip` + `CR-001` + 资源原因**。四引擎全部GPU通过的联合结论不可宣称。这些子项不再作为M0/M2/M3/M6的完成阻塞项，但安装、导入、诊断、精准修复、隔离/回退及受限硬件拒绝行为仍须验证；如真实导入本身受驱动阻断，保持blocked并另列具体事实，不自动扩展skip。
- 最小范围：Kohya、AI Toolkit本机可执行的GPU/真实短训练，以及DiffSynth配方内普通Torch小张量验证，仍保留原技术门；TE显存超限不等于小张量不能运行。不能把没有合适Fast/DiffSynth机器扩成全部测试豁免。M0独立P3准备超时记录不改为pass；不再为四引擎GPU前提重复下载独立Torch，基础CUDA与架构探针由M2/M3在相应真实配方中先验证，再训练。产品仍不得将“安装完整/可导入/设备识别”当作GPU可用或已训练。
- M0资源核查新口径：P2保留四引擎配方/许可/组件大小和硬件限制，跳过项的大模型不下载、不换弱模型；未豁免的OS/工具/安装依赖仍须有可信预算。P3历史not-run作为首次失败保留，其独立GPU前置合同由本CR分期取代，不在M0额外重跑。**干净Windows、WebView2、A1、A2–A5、A7–A10、同一最终制品、原生UI、用户资料保护、签名及阶段push都没有豁免。**
- 影响范围：D6、A6的Fast/DiffSynth GPU子项、P2/P3资源前置及相关EXIT-M0/M2/M3/M6；GATE-11/14继续检查未豁免项。A6须拆项报告，剩余必测通过且授权skip齐备时允许阶段`done`并标`pass-with-boundary`；整体交付只能称“完成（含用户批准的GPU验收边界）”，不能称四引擎GPU全通过。所有其他not-run/unknown/blocked/skip仍阻止相应完成门。
- 风险：P1验收证据缺口经用户授权接受，Fast/DiffSynth端到端训练能力未验证，不能宣传该实测结论。豁免测试不能授权绕过产品路径/信任/事务守护、伪标healthy/known_good、修改host驱动/全局配置或借用远程资源。
- 资源/回退：原网络200GiB、F峰值300GiB、GPU180分钟及各阶段额度不增加；仅重算实际仍需下载的资源。全部0.1首次失败、partial、元信息、已推送历史保留；以后有资源可新attempt补证据，原skip不倒填为历史pass。
- Goal连续性：现有Goal已随用户回复恢复active。工具只支持更新状态，无法改现有objective正文；后来的用户指令及本CR优先于该正文中的0.1“四引擎GPU全通过”旧要求，不创建重复Goal或虚标complete。全程提示词、总控与阶段入口同步本CR。
- 唯一下一动作：继续补齐M0未豁免的干净Windows与预算路径，独立复审并保存基线后进入M1。

## 触发条件

以下变化需要先记录变更：目标范围、三页行为、目录/数据/IPC合同、迁移与回退、签名信任、已锁定决策、支持平台、资源预算、阶段顺序、测试矩阵、最终同制品身份、任何必测项或完成阈值。普通函数拆分、命名和保持合同的实现方式由执行者判断，不转成重复审批。

## 记录结构与处置

每项`CR-001...`记录原要求、证据、拟改内容、影响的A1–A10/阶段/gate、P0/P1/P2/P3、替代验证、回退、授权状态/依据、下一动作。执行期间记录置于证据根`changes/`，总控决策记录保留摘要和链接。

- P0：可能破坏真实用户资料、不可恢复控制状态或信任边界，立即停止相关变更。
- P1：未获用户批准的必需能力或真实验收缺口不得降阈值、删测试或标skip继续交付。CR-001仅对逐项列明的GPU验收授权skip，其余P1继续阻断。
- P2/P3：预算和合同内可自主修正，补测试/证据并记录；改变用户批准范围则仍需用户决定。

发现与规格冲突时，先用最小可验证证据复现，再提出具体改稿；不能靠改Goal弱化主计划。影响后续阶段时同步改规格、总控、manifest、目标、任务书、清单、Goal和gate。用户指定的最终从零实测不能默认豁免。

## 连续性和版本

保留阶段ID M0–M6；改名必须记录旧名/新名和证据映射，已有done阶段不静默重开或删除。重跑属于新run-id，保留原失败与修复后结果，不覆盖历史原始日志。文档生成本轮是v0.1；批准、架构或验收变更时升版本并注明理由。

本计划新增M6来自用户明确要求，原M0–M5继续沿用设计含义。用户已启动执行，CR-001是唯一获批GPU测试豁免；没有预算超限、干净OS或其他验收豁免。旧规划轮的未批准文字作为历史语境保留，不覆盖后续用户指令。

## 完成与上下文

每次阶段退出、遇到阻塞和切会话前，先同步总控台账与唯一下一动作。用户要求约60%准备、最晚70%前完成压缩；无法精确读比例时按文件量、历史长度和复杂度主动执行。精简摘要至少保留目标、完成项、关键决策、路径/改动、待办、风险/阻塞/待确认；恢复时只读摘要、总控及当前阶段必要文件。
