# 固定版本目录与下载来源

`releases.json` 随启动器嵌入，界面只能选择其中的版本 ID；运行时不接受任意下载 URL。`main` 和 `dev` 表示取样时的分支来源，版本号来自各归档内的 `VERSION`，不将 `main` 自动解释成稳定发布版。

2026-10-28 通过代理 `http://127.0.0.1:11809` 实时读取 `refs/heads/main`，得到 `0785419e7dc1a3058bd8710a9aa933fec0aabdee`；此前已核验的 `dev` 是 `9ca2de963122f34599e34e5ff382199de9188811`。两份 HTTPS 固定提交归档均已完整下载，SHA256、压缩字节和 ZIP 条目解压字节总数来自实际测量。GitHub 源码归档未提供独立校验清单，因此源码哈希的信任来源是本次固定提交 HTTPS 下载，不宣称独立官方签名认证。

uv 0.11.16 ZIP 哈希已与同 URL 后附 `.sha256` 的官方文件核对；`exe_sha256` 由该已校验 ZIP 内的 `uv.exe` 流式计算。Python 由已校验的 uv 按指定版本管理，并在准备后实际执行检查。

目录 schema、profile schema 和环境配方标识分别管理。两个取样提交均使用 `legacy-view-v1` 数据合同：不可变源码与共享 profile 分离，由启动器创建兼容运行视图。未知 schema 或未知数据合同拒绝变更。后续发布需更新固定提交和实测哈希，不能只改版本显示文字。

## 签名清单协议与生产启用边界

上文保留首轮取样的来源记录；当前候选身份以本包 `releases.json`、固定配方和源码索引为准。`src-tauri/src/signed_catalog.rs` 实现独立的签名清单与可信历史协议。生产公钥和发布端点尚未登记，普通模式继续使用内置目录和手动升级；本次未生成维护者私钥、签署生产版本或发布网络资产。

封套字段为 `schema_version / key_id / payload / signature_hex`。签名算法为 Ed25519，签名对象是 `payload` 字符串解码后的精确 UTF-8 字节；签名与公钥使用固定长度小写十六进制。`nt-catalog-json-v1` 使用代码中 `Payload` 结构的字段顺序、紧凑 JSON、无 BOM、无额外空白，嵌套对象同样遵守各结构的固定字段顺序。校验器解析后重新编码并逐字节比较，拒绝未知字段、重复字段、非规范转义与浮点数；修改协议结构需要新的 schema/encoding 审核，不能只调整发布脚本的字段顺序。

payload 包含发布序号、生效和到期时间、平台、最低壳版本、资料 schema、发布资产、配方摘要、动作 ID、轮换公钥及撤销项。版本/公钥/撤销列表使用规定的升序且不重复。资产仍须通过固定提交 URL、大小、摘要和内置配方约束；当前签名适配只授权已编译 GUI 配方及 `download_source / isolated_entry_probe / uv_locked_sync / uv_venv / verify_environment` 动作，不能包含命令、脚本或任意解释器参数。签名本身不会激活版本或继承旧健康状态。

维护者正式启用时按以下顺序操作：

1. 在启动器仓库之外保管生产 Ed25519 私钥；通过独立渠道核对公钥指纹和发布者身份。提交审查只登记公钥、key ID、固定 HTTPS 端点与平台/动作范围，不提交私钥。生产根、端点和序号空间须与公开测试根分离，并通过程序发布变更启用；UI 没有填写任意 URL、公钥或命令的入口。
2. 冻结源码提交、已编译前端、工具、依赖和配方摘要，核对实际字节预算与来源。使用生产 encoding/schema 构建规范 payload，序号必须严格大于该发布空间此前已接受的最高序号。校验有效期、最低壳版本与资料合同后，离线签署并保存封套原文；镜像只能分发相同签名制品，不能重新决定版本身份。
3. 发布前以干净工作区校验封套、每个资产摘要和拒绝分支，再提供给用户显式选择。客户端持锁后一次提交可信历史，保存原始封套、payload 摘要、接受序号/时间依据和接受前的完整公钥表。下载、准备或校验失败保持既有绑定；更新发现应在后台运行。
4. 轮换时先由仍可信的旧 key 签署更高序号清单，将新的唯一 key ID 和公钥加入 `rotations`；下一份清单才使用新 key 签署。既有 key ID 不得换公钥，已撤销的公钥不得换别名复活。保留旧公钥和轮换封套，供历史离线重验；不直接覆盖本地公钥文件。
5. 安全撤销使用经可信 key 签署的更高序号 `revoked_keys / revoked_releases`。撤销持续生效，不能用主动选旧版、回退或旧镜像绕过；只保留实体和资料供诊断，不自动删除。过期和下架仅停止新增安装推荐/信任，不推断本地既有制品遭到安全撤销。撤销最后可用签名根后的恢复需要另行审查的壳发布或既定可信恢复渠道，不能临时接收 UI 公钥。

当前时间依据为系统 UTC：新接受清单拒绝尚未生效、过期和相对于已接受时间回退的时钟。离线重验使用当次保存的接受时间重新验证签名链，不因为今天已超过旧清单有效期而丢弃历史身份；新增安装仍检查当前有效性。此依据不代表外部可信时间服务。

## 同包固定签名夹具

`signed-fixtures-v1.json` 只包含公开测试封套。测试公钥来自 [RFC 8032 的公开 Ed25519 向量](https://www.rfc-editor.org/rfc/rfc8032#section-7.1)，对应材料是公开测试数据，不是维护者签名身份；仓库中没有维护者私钥。普通工作区拒绝这些封套。只有用户显式选择 `signed-catalog-v1`，且后端确认全新的正式标记工作区、默认空 profile、固定根/端点/动作后，才能创建绑定当前 EXE 摘要的沙盒会话；会话配置不提供修改入口。

固定 case 覆盖有效签名、旧根授权后轮换、已知撤销、篡改、过期、错误平台和重放。`shell-self-copy-policy` 仅授权新沙盒内 `shell-fixture/current/NextTrainerLauncher.exe` 与 `shell-fixture/candidate/NextTrainerLauncher.exe` 的本包同 SHA、同字节自复制，供同一交付壳验证独立 helper 的替换/恢复事务。它不授权生产壳更新；helper 仍须独立验签固定 policy、核对会话与所有路径，并重新计算实际文件摘要，不能信任 JSON 中的成功标志。
